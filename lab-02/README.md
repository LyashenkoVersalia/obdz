| Дія | Повідомлення або результат СУБД | Кількість записів |
|---|---|---|
| Перший запуск seed-data.sql | У DBeaver: Queries 9, Updated Rows 55; без помилок | Як у розділі 2, разом 58 |
| Другий запуск seed-data.sql | Queries 9, Updated Rows 0; без помилок | У кожній таблиці без змін, разом 58 |
| Окрема команда INSERT для orders з ON CONFLICT | Updated Rows 0, що відповідає INSERT 0 0 | orders: 10 |
| Та сама команда без ON CONFLICT | ERROR: duplicate key value violates unique constraint "orders_order_number_key" | orders: 10, нові записи не додано |

Кожну таблицю захищає обмеження, наведене в розділі 1. Для order_items використано складений первинний ключ (order_id, product_id); для решти таблиць — UNIQUE на відповідних стовпцях.

ON CONFLICT (...) DO NOTHING пропускає записи, які порушили б обране обмеження унікальності. Без ON CONFLICT повторна вставка завершується помилкою.

Повторний запуск скрипта не змінює кількості записів і не завершується помилкою, тому наповнення є ідемпотентним. Лічильники IDENTITY можуть збільшуватися навіть для пропущених вставок; це не означає появу нових записів.

### Запити з NULL

Початковий запит не включає покупців без телефону:

```sql
SELECT id, last_name, phone
FROM customers
WHERE phone <> '+380000000001'
ORDER BY id;
```

Результат: 2 рядки — покупці 3 та 5.

Виправлений запит явно включає покупців без телефону:

```sql
SELECT id, last_name, phone
FROM customers
WHERE phone <> '+380000000001'
   OR phone IS NULL
ORDER BY id;
```

Результат: 4 рядки — покупці 2, 3, 4 та 5.

У SQL умова може мати значення «істина», «хибність» або «невідомо». Порівняння NULL із номером телефону дає «невідомо», а WHERE залишає лише рядки зі значенням «істина». У виправленому запиті phone IS NULL дає істину для покупців без телефону, тому вони потрапляють до результату.

## 5. Запити зі з’єднанням таблиць

Файл: [queries.sql](queries.sql)

Запити виконано після початкового наповнення бази, до виконання змін даних.

### З’єднання 1. Внутрішнє з’єднання двох таблиць

Питання: які аромати належать кожному бренду?

```sql
SELECT
    f.id AS fragrance_id,
    f.name AS fragrance_name,
    b.name AS brand_name
FROM fragrances AS f
JOIN brands AS b
    ON f.brand_id = b.id
ORDER BY f.id;
```

Отримано 6 рядків — по одному на кожен аромат.

Кожен аромат має обов’язковий зовнішній ключ fragrances.brand_id, який посилається на первинний ключ brands.id. Тому кожен аромат знаходить рівно один бренд.

Бренд Amber Studio не потрапив до результату, оскільки ще не має ароматів.

### З’єднання 2. Відновлення таблиці «Продажі»

Питання: як отримати відомості про продажі у структурі «поганої» таблиці з розділу 5 лабораторної роботи №1?

```sql
SELECT
    o.id AS order_id,
    o.ordered_at AS ordered_at,
    o.status AS order_status,
    c.id AS customer_id,
    c.last_name AS last_name,
    c.email AS email,
    c.phone AS phone,
    p.id AS product_id,
    p.volume_ml AS volume_ml,
    pf.name AS format_name,
    p.price AS price,
    f.id AS fragrance_id,
    f.name AS fragrance_name,
    f.description AS description,
    b.id AS brand_id,
    b.name AS brand_name,
    oi.quantity AS quantity,
    oi.unit_price AS unit_price,
    pay.id AS payment_id,
    pay.amount AS amount,
    pay.paid_at AS paid_at,
    pay.status AS payment_status,
    s.id AS shipment_id,
    s.address AS address,
    s.shipped_at AS shipped_at,
    s.status AS shipment_status
FROM order_items AS oi
JOIN orders AS o
    ON oi.order_id = o.id
JOIN customers AS c
    ON o.customer_id = c.id
JOIN products AS p
    ON oi.product_id = p.id
JOIN product_formats AS pf
    ON p.format_id = pf.id
JOIN fragrances AS f
    ON p.fragrance_id = f.id
JOIN brands AS b
    ON f.brand_id = b.id
LEFT JOIN payments AS pay
    ON pay.order_id = o.id
LEFT JOIN shipments AS s
    ON s.order_id = o.id
ORDER BY o.id, p.id;
```

Отримано 12 рядків — по одному на кожен запис order_items.

Обов’язкові зв’язки із замовленням, покупцем, товаром, форматом, ароматом і брендом забезпечують рівно одну відповідність для кожної позиції.

Оплати й доставки приєднано через LEFT JOIN, оскільки вони можуть бути відсутні. Обмеження UNIQUE на payments.order_id та shipments.order_id не дозволяють цим з’єднанням множити рядки. За відсутності оплати або доставки відповідні стовпці містять NULL.

Замовлення 1, 3 і 9 мають по дві позиції, тому кожне з них представлене двома рядками. Замовлення 10 відсутнє, оскільки не має позицій.

Логічний порядок виконання:

1. FROM і JOIN: беруться позиції замовлень та приєднуються пов’язані записи восьми інших таблиць.
2. WHERE: відсутній, додаткова фільтрація не виконується.
3. SELECT: формуються 26 стовпців у початковому порядку таблиці «Продажі» роботи №1. Псевдоніми записано англійською, малими літерами, через підкреслення, без лапок.
4. ORDER BY: результат упорядковується за ідентифікаторами замовлення та товару. Разом вони утворюють унікальний ключ позиції, тому порядок однозначний. LIMIT відсутній.

Зміст і порядок 26 стовпців відповідають «поганій» таблиці з розділу 5 роботи №1. Українським назвам її стовпців відповідають англійські псевдоніми SQL. Значення інші, оскільки використано навчальні дані роботи №2.

Новий номер замовлення order_number та ідентифікатор формату не виводяться, бо їх не було серед початкових 26 стовпців. Назва формату отримується з довідника product_formats.

Відомості про покупця, замовлення, оплату й доставку повторюються в результаті для кожної позиції замовлення. У нормалізованій базі ці відомості зберігаються окремо, а широка таблиця формується запитом.

Поточна ціна products.price та історична ціна order_items.unit_price виводяться окремо, оскільки мають різний зміст. Зміна поточної ціни товару не повинна змінювати ціну вже оформленої позиції.

### З’єднання 3. Рядки без пари

Питання: які покупці ще не мають жодного замовлення?

```sql
SELECT
    c.id AS customer_id,
    c.last_name,
    c.email
FROM customers AS c
LEFT JOIN orders AS o
    ON o.customer_id = c.id
WHERE o.id IS NULL
ORDER BY c.id;
```

Отримано 1 рядок: покупець 5, Тестовий-Д, customer05@example.com.

LEFT JOIN зберігає всіх покупців, зокрема тих, які не мають замовлень. Умова WHERE o.id IS NULL залишає лише покупців без відповідного замовлення.

Стовпець orders.id є первинним ключем і не може містити NULL у наявному записі, тому така перевірка коректно визначає відсутність пари.

## 6. Зміна і видалення даних

Файл: [data-changes.sql](data-changes.sql)

Кожен дослід виконано в окремій явній транзакції. Перед зміною виконано SELECT для перевірки вибраних записів, після зміни — SELECT для перевірки результату. Наприкінці виконано ROLLBACK і перевірено відновлення початкових даних.

| Зміна | Рядків у SELECT до / після зміни / після ROLLBACK | Повідомлення DBeaver | Завершення |
|---|---|---|---|
| UPDATE: пробна знижка 10% на мініатюри | 2 / 2 / 2 | Updated Rows: 2 | ROLLBACK |
| UPDATE: додавання відсутнього опису Wood Rain | 1 / 1 / 1 | Updated Rows: 1 | ROLLBACK |
| DELETE: видалення квітневих замовлень-чернеток | 1 / 0 / 1 | Updated Rows: 1 | ROLLBACK |

У першому UPDATE ціни товарів 4 і 9 змінилися з 650 та 800 грн на 585 та 720 грн. Після ROLLBACK відновлено ціни 650 та 800 грн. Кількість рядків не змінилася, оскільки UPDATE змінює значення наявних записів.

У другому UPDATE опис аромату Wood Rain змінився з NULL на «Деревний аромат із нотами дощу». Після ROLLBACK опис знову дорівнює NULL.

DELETE відібрав замовлення ORD-2026-010 зі статусом draft за квітень 2026 року. Після видалення SELECT повернув 0 рядків, а після ROLLBACK замовлення відновлено.

Умови відбору основних UPDATE та DELETE використовують формат товару, назву й відсутність опису аромату, статус і дату замовлення, а не лише первинні ключі.

### Реакції на видалення

| Зв’язок | Реакція | Що сталося з пов’язаними рядками | Повідомлення СУБД або DBeaver |
|---|---|---|---|
| customers → orders | RESTRICT | Видалення покупця 1 заборонено через наявні замовлення 1, 4 і 9. Після ROLLBACK покупець і всі три замовлення збережені. | SQL Error [23001]: порушено RESTRICT для orders_customer_id_fkey |
| orders → order_items | CASCADE | Видалення замовлення 9 автоматично видалило дві його позиції з товарами 1 і 4. Після ROLLBACK замовлення та обидві позиції відновлено. | DELETE замовлення: Updated Rows: 1; SELECT позицій: 2 → 0 → 2 |

Для RESTRICT отримано повідомлення:

`ERROR: update or delete on table "customers" violates RESTRICT setting of foreign key constraint "orders_customer_id_fkey" on table "orders"`

Для перевірки CASCADE використано замовлення 9, яке не має оплати й доставки, тому інші зовнішні ключі не заборонили його видалення.

Updated Rows: 1 під час видалення замовлення показує безпосереднє видалення одного запису orders. Автоматичне видалення двох записів order_items підтверджено окремим SELECT.

У моделі використано реакції RESTRICT та CASCADE; обидві перевірено. Після завершення дослідів початкові дані відновлено.

## 7. Явні транзакції

Файл: [transactions.sql](transactions.sql)

Операція предметної області: реєстрація оплати замовлення та переведення замовлення у стан paid.

Операція змінює дві таблиці: у payments додається оплата, а в orders змінюється стан замовлення. Ці зміни потрібно виконувати разом, щоб не залишити частково виконану операцію.

### Частина 1. COMMIT

Для замовлення ORD-2026-006 сума оплати становить 1600 грн:
дві одиниці товару по 800 грн.

Перед контрольним повтором замовлення 6 повернуто у стан new,
а оплату попереднього досліду видалено. Початковий стан перевірено
з незалежного сеансу Б.

У сеансі А виконано BEGIN, INSERT INTO payments та UPDATE orders.
INSERT і UPDATE повернули Updated Rows: 1 кожна.

| Момент перевірки | Сеанс | Стан замовлення | Сума оплати | Стан оплати |
|---|---|---|---|---|
| До операції | Б | new | NULL | NULL |
| Після змін, до COMMIT | А | paid | 1600 | paid |
| До COMMIT сеансу А | Б | new | NULL | NULL |
| Після COMMIT сеансу А | Б | paid | 1600 | paid |

До COMMIT зміни були видимі в сеансі А, але не були видимі
в незалежному сеансі Б. Після COMMIT повторний SELECT у сеансі Б
показав обидві збережені зміни: оплату 1600 грн та стан замовлення paid.

### Частина 2. ROLLBACK

Для замовлення ORD-2026-008 виконано ту саму операцію із сумою 540 грн: три одиниці товару по 180 грн.

Усередині транзакції додано оплату та змінено стан замовлення на paid. INSERT повернув Updated Rows: 1. SELECT показав стан замовлення paid, суму 540 грн і стан оплати paid.

Після ROLLBACK SELECT показав стан замовлення new та NULL у стовпцях приєднаної оплати. Вставку оплати й зміну стану замовлення скасовано разом.

### Частина 3. Помилка всередині транзакції

Для замовлення ORD-2026-009 спочатку змінено стан на paid. Друга команда намагалася додати оплату зі значенням amount = NULL, що порушує NOT NULL.

| Команда | Результат |
|---|---|
| BEGIN | Початок транзакції |
| UPDATE orders для замовлення 9 | Зміна виконана; SELECT показав paid |
| INSERT INTO payments з amount = NULL | SQL Error [23502]: null value in column "amount" of relation "payments" violates not-null constraint |
| Наступний SELECT | SQL Error [25P02]: current transaction is aborted, commands ignored until end of transaction block |
| COMMIT | Транзакція завершена; наступний SELECT підтвердив відкат першої зміни |

У статистиці DBeaver зазначено відправлену команду COMMIT. Окремий текст відповіді сервера ROLLBACK на скриншоті не відображено; відкат підтверджено станом даних після завершення.

Підсумковий результат:

| Замовлення | Стан замовлення | Сума оплати | Стан оплати |
|---|---|---|---|
| 6 | paid | 1600 | paid |
| 8 | new | NULL | NULL |
| 9 | new | NULL | NULL |

Перша зміна замовлення 9 не збереглася, хоча до помилки SELECT показував paid. Помилка другої команди призвела до відкату всієї транзакції. Це демонструє атомарність.

NULL у результаті LEFT JOIN для замовлень 8 і 9 означає відсутність відповідних записів payments.

## 8. Втрачене оновлення

Файл: [lost-update.sql](lost-update.sql)

Для дослідів використано стовпець `products.price` товару з `id = 1`.
Перед кожним дослідом ціну встановлено на 2500 грн.

Сеанс А зменшує ціну на 10 %, сеанс Б підвищує її на 300 грн.
Очікуваний результат для послідовного застосування змін А, потім Б:
2500 × 0,90 + 300 = 2550 грн.

Використано два незалежні з'єднання з базою `dbsa`:
сеанс А — редактор `Script-4`, сеанс Б — редактор `Script-5`.
Під час початкової перевірки `pg_backend_pid()` повернув 88 та 90
відповідно. Різні PID підтвердили незалежність сеансів.
Для перевірки рівня ізоляції використано `SHOW transaction_isolation`.

### Дослід 1. READ COMMITTED

Кожен сеанс обчислює нову ціну за прочитаним значенням
і записує готове число.

| Крок | Сеанс А | Сеанс Б |
|---|---|---|
| 1 | BEGIN READ COMMITTED; SELECT: 2500 | — |
| 2 | — | BEGIN READ COMMITTED; SELECT: 2500 |
| 3 | UPDATE: запис 2250; змінено 1 рядок | — |
| 4 | Транзакція відкрита | UPDATE: запис 2800; очікування блокування |
| 5 | COMMIT | Очікування завершується; Updated Rows: 1 |
| 6 | — | COMMIT; SELECT: 2800 |

Значення в базі наприкінці: **2800 грн замість 2550 грн**.
Сеанс Б записав число, обчислене за старою ціною 2500,
і перезаписав результат знижки сеансу А.

### Дослід 2. REPEATABLE READ

Обидва сеанси почали транзакції командою
`BEGIN ISOLATION LEVEL REPEATABLE READ;`
і прочитали початкову ціну до зміни сеансом А.

| Крок | Сеанс А | Сеанс Б |
|---|---|---|
| 1 | BEGIN REPEATABLE READ; перевірка рівня; SELECT: 2500 | — |
| 2 | — | BEGIN REPEATABLE READ; перевірка рівня; SELECT: 2500 |
| 3 | UPDATE: запис 2250; змінено 1 рядок | — |
| 4 | Транзакція відкрита | UPDATE: спроба запису 2800; очікування блокування |
| 5 | COMMIT | Помилка 40001: could not serialize access due to concurrent update |
| 6 | — | ROLLBACK |
| 7 | — | Нова транзакція REPEATABLE READ; SELECT: 2250 |
| 8 | — | Новий розрахунок 2250 + 300; UPDATE: 2550; COMMIT |
| 9 | SELECT з іншого сеансу: 2550 | — |

Значення в базі наприкінці: **2550 грн**.
Спробу запису за застарілим знімком відхилено.
Після ROLLBACK сеанс Б повторив транзакцію з початку,
прочитав 2250 і перерахував нове значення.

### Дослід 3. Зміна відносно поточного значення

Обидві транзакції працювали на рівні READ COMMITTED.
Розрахунок виконано безпосередньо в UPDATE:
у сеансі А — `price = round(price * 0.90, 2)`,
у сеансі Б — `price = price + 300`.

| Крок | Сеанс А | Сеанс Б |
|---|---|---|
| 1 | BEGIN READ COMMITTED; SELECT: 2500 | — |
| 2 | — | BEGIN READ COMMITTED; SELECT: 2500 |
| 3 | UPDATE: price = round(price * 0.90, 2); змінено 1 рядок | — |
| 4 | Транзакція відкрита | UPDATE: price = price + 300; очікування блокування |
| 5 | COMMIT | UPDATE успішно завершується; Updated Rows: 1 |
| 6 | — | COMMIT |
| 7 | SELECT з іншого сеансу: 2550 | — |

Значення в базі наприкінці: **2550 грн**.
Після очікування сеанс Б обчислив підвищення від ціни 2250,
збереженої сеансом А. Помилки серіалізації не виникло.

### Висновок

У першому досліді втрачено зміну сеансу А, оскільки сеанс Б
записав готове число, розраховане за раніше прочитаною ціною.

У другому досліді REPEATABLE READ не дозволив перезаписати
рядок, змінений після отримання знімка сеансом Б.
Для збереження обох змін довелося повторити всю транзакцію Б
з новим читанням і розрахунком.

У третьому досліді відносний UPDATE на READ COMMITTED
після очікування застосував підвищення до актуальної версії рядка.
Для перевіреного порядку виконання обидві зміни збережено.

Після завершення дослідів початкову ціну товару відновлено до
2500 грн та перевірено окремим SELECT.

### Перевірка незалежності ароматів від порядку брендів

Після зауваження на захисті виправлено seed-data.sql:
brand_id для кожного аромату тепер визначається підзапитом
за унікальною назвою бренду, а не задається готовим числом.
Тому перестановка рядків брендів не змінює належність ароматів.

Наприклад, для Rose Mist використано:
SELECT id FROM brands WHERE name = 'Aroma North'.

UNIQUE (name) гарантує не більше одного результату пошуку.
Бренди додаються перед ароматами. Якщо потрібного бренду немає,
підзапит поверне NULL і вставку відхилить NOT NULL на brand_id.

Перевірка: [check-brand-order.sql](check-brand-order.sql).

У перевірочній копії Velvet Lab додано перед Aroma North.
Блоки наповнення брендів і ароматів виконано двічі
у порожніх тимчасових таблицях.

| Аромат | brand_id у перевірці | Фактичний бренд | correct_brand |
|---|---:|---|---|
| Rose Mist | 2 | Aroma North | true |
| Citrus Dawn | 2 | Aroma North | true |
| Amber Night | 1 | Velvet Lab | true |
| Wood Rain | 1 | Velvet Lab | true |
| Vanilla Cloud | 3 | Serein Atelier | true |
| Iris Light | 3 | Serein Atelier | true |

Після двох запусків: 4 бренди та 6 ароматів, дублікатів немає.
Статистика DBeaver: Queries — 9, Updated Rows — 10.
Перевірку завершено ROLLBACK; постійні таблиці не змінювалися.

Підтверджено стійкість зв'язку fragrances → brands
до перестановки брендів. Інші залежні вставки поки використовують
заздалегідь визначені числові ідентифікатори, тому незалежність
усього наповнення від довільної перестановки рядків не заявляється.
